## Architecture Review

Phase 4G adds a two-layer quality system without changing production authentication, permissions, backend behavior, or business workflows.

### Layer 1 — Protected in-product QA command center

`public/qa-v2.html` now provides authenticated diagnostics for:

- Firebase session presence
- canonical role resolution
- page-policy coverage
- theme runtime and material authority
- design-system bundle version
- design-system registry coverage
- navigation mounting
- horizontal overflow
- duplicate DOM IDs
- reduced-motion support
- network and service-worker capability
- authorized critical-route responses
- light, dark, system, and image appearance previews
- desktop, tablet, iPhone, and Android project coverage
- repository audit findings
- exportable JSON diagnostics

The page remains restricted to platform administrators, owners, and administrators.

### Layer 2 — External authenticated visual regression harness

`tests/visual/` uses Playwright to:

1. Log in through the real EvaraOS login form.
2. Wait for the verified Firebase and Firestore route guard.
3. Save temporary browser authentication state, including IndexedDB.
4. Open only routes authorized for the tested role.
5. Apply deterministic appearance state before page boot.
6. Disable animation and caret noise for capture.
7. Check HTTP status, route retention, application readiness, overflow, keyboard focus, page errors, console errors, duplicate IDs, and accessible control names.
8. Compare viewport screenshots against reviewed baselines.
9. Retain traces, videos, reports, and failure screenshots without uploading authentication state.

## Current Risks

### Baselines do not exist yet

The harness and CI workflow are committed, but screenshots cannot be approved until the workflow is run against a deployed QA environment with dedicated Firebase accounts.

### QA secrets are not configured by code

The following must be configured in GitHub repository secrets:

- QA base URL
- owner email and password
- optional credentials for platform administrator, administrator, manager, sales, technician, cleaner, customer, and vendor

The owner account is mandatory. Full role enforcement is optional until all synthetic accounts exist.

### Dynamic business content can still create visual noise

The test masks maps, iframes, video, timestamps, live indicators, and common realtime counters. New nondeterministic content must receive a narrow mask or a stable fixture. Complete cards or page regions should not be hidden merely to make a test pass.

### Existing product diagnostics may initially fail

The first authenticated run may reveal:

- duplicate IDs
- console errors
- role-route redirects
- horizontal overflow
- missing accessible labels
- unstable screenshots
- appearance-specific contrast issues

These should be treated as product findings, not test-harness defects, unless the harness is demonstrably incorrect.

## Impact Assessment

### Positive impact

- Introduces repeatable visual regression testing.
- Tests real authentication instead of a mocked role.
- Preserves route-guard and Firestore profile verification.
- Covers all canonical roles.
- Covers all universal appearance modes.
- Covers desktop, tablet, iPhone, and Android layouts.
- Produces downloadable CI evidence.
- Adds automatic design-system ownership checks on relevant repository changes.
- Gives administrators an in-product QA dashboard.
- Creates a controlled process for approving screenshot baseline changes.

### Change risk

The automated visual job is manual and read-only. It does not create, update, or delete production records. However, pages may perform their normal read operations and client initialization. Dedicated synthetic QA accounts and a non-sensitive QA environment remain strongly recommended.

The in-product appearance controls use the existing theme runtime. They do not introduce a second appearance engine.
